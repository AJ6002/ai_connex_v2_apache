1. Executive Summary
The AI-ConneX Data Studio Data Profiler is the intelligence layer immediately after the Data Studio Compiler. The Compiler converts heterogeneous industrial source material into a validated, unified dataset. The Profiler then determines what the compiled dataset actually contains: its structure, semantics, statistical characteristics, quality indicators, relationships, temporal behavior, units, cardinality, distributions and suitability for downstream industrial AI workflows.
The Profiler also reconnects the technical facts discovered from the dataset with the intent established by the AI-ConneX Chatbot and the operational decisions made by the Compiler. These combined facts become a single machine-readable identity document called manifest-UID.json.
The key architectural idea is that a dataset is not considered fully understood merely because it has been normalized. The Compiler answers 'Can we make this data structurally usable?'; the Profiler answers 'What is this data, how does it behave, how reliable is it, and how does it relate to the user's industrial objective?'

3. What the Data Profiler Receives
3.1 Primary Input from Compiler
{  "dataset_id": "ACX-CMP-00042",  "artifact": "dataset.parquet",  "schema": "schema.json",  "metadata": "metadata.json",  "lineage": "lineage.json",  "compilation_report": "compilation_report.json",  "status": "SUCCESS"}
The Profiler should trust the Compiler's artifact contract but independently verify critical properties. The Compiler's report is evidence about transformation; it is not a substitute for profiling.
3.2 User Intent from Previous Chatbot Stage
{  "intent_id": "ACX-INT-00042",  "industrial_domain": "manufacturing",  "objective": "predict machine failure",  "target_entity": "CNC machine",  "important_signals": ["temperature", "vibration", "motor_speed"],  "time_horizon": "next 24 hours",  "constraints": {    "preserve_source_context": true,    "explainability": "required"  }}
This intent is carried forward rather than discarded. It allows the Profiler to distinguish between generic data statistics and statistics that matter to the industrial objective.

6. R&D Problem Definition
Traditional profiling tools generally answer generic questions: number of rows, columns, data types, null counts, unique values, descriptive statistics and distributions. Industrial AI-ConneX requires a broader concept of profiling because industrial datasets are usually temporal, sensor-driven, multi-asset, unit-dependent and purpose-specific.
6.1 R&D Questions
How can the Profiler automatically characterize heterogeneous industrial variables after normalization?
How can generic statistics be transformed into industrially meaningful metadata?
How can the Profiler distinguish a useful sensor signal from an identifier, categorical label or administrative field?
How can time-series properties such as sampling frequency, gaps, irregular intervals and drift be detected automatically?
How can data quality be quantified without pretending that statistical quality equals engineering correctness?
How can the user's original objective influence which profiling checks receive priority?
How can the resulting metadata become a stable manifest that downstream AI-ConneX modules can consume?
7. Research Foundation
Data profiling has a strong foundation in data quality, schema discovery, metadata management and data integration research. AI-ConneX extends this foundation by making profiling intent-aware and industrial-domain-aware.

11. Industrial / Sensor Profiling
For industrial sensor data, generic statistics are insufficient. The Profiler should additionally inspect:
Sampling interval and approximate sampling frequency.
Irregular timestamps.
Missing time windows.
Flat-line sensors.
Constant-value sensors.
Sudden spikes and discontinuities.
Out-of-range observations where engineering limits are known.
Sensor drift and distribution shift.
Noise indicators.
Unit consistency.
Machine/asset/channel cardinality.
Cross-sensor correlation and lag relationships.
12. Semantic Profiling
Semantic profiling attempts to determine what a field represents, independently of its raw column name. The Profiler can combine canonical names from the Compiler, datatype, units, value ranges, naming patterns, metadata, and domain vocabulary.
Example:Column: temperatureType: floatUnit: °CRange: 21.2–94.7Context: CNC machineCorrelation: bearing_vibrationSemantic classification:asset_signal.temperaturemeasurement_type = temperatureengineering_domain = machine_health
13. Intent-Aware Profiling
A central AI-ConneX feature is that the Profiler does not treat all columns equally. If the user's objective is predictive maintenance, vibration, temperature, current, pressure and RPM may receive deeper analysis than an administrative operator ID.

15. How AI-ConneX Overcomes the Failures
Use deterministic computation for all numeric statistics.
Separate observed facts from inferred semantics.
Attach confidence and provenance to inferred metadata.
Preserve source and Compiler lineage.
Use domain-specific profiling policies.
Perform temporal checks for datasets containing timestamps.
Detect candidate identifiers before feature-quality scoring.
Never delete anomalies simply because they are statistically unusual.
Distinguish data-quality warnings from hard failures.
Version every manifest and profile execution.
Make the manifest reproducible from dataset hash + profile configuration + profiler version.
Use an agent only for interpretation and prioritization, not for arithmetic.
16. Profile Assignment
Every successful profiling run receives a Profile UID. The UID identifies the profile execution and allows downstream systems to distinguish different versions of the same underlying dataset.
Profile UID example:ACX-PROF-20260814-7F31A2C9Recommended identity inputs:dataset_hashcompiler_job_idprofile_config_hashprofiler_versionexecution_timestamp
The Profile UID should not replace the Dataset UID. Dataset identity, compilation identity and profiling identity should remain separately traceable.

31. Important Architectural Distinction
The Profiler does not overwrite the user's intent with what it discovers. It stores intent and observed reality as separate evidence layers. If the user asks for machine-failure prediction but the dataset contains no credible failure label, the manifest should say exactly that. The system should not invent a target variable.
intent.objective = "predict_machine_failure"profile.finding:  candidate_target = null  reason = "No validated failure-event label detected"manifest.readiness:  status = "REVIEW_REQUIRED"
32. Security, Governance and Compliance Design
Do not expose raw industrial data to an external LLM unless explicitly authorized.
Prefer sending schema summaries, samples or metadata to the agent rather than complete datasets.
Record which metadata was supplied to the agent.
Hash datasets and manifests for integrity.
Keep source artifacts immutable.
Use role-based access control.
Encrypt data in transit and at rest.
Separate tenant/customer namespaces.
Record profiler execution identity and configuration.
Maintain retention policies appropriate to industrial data.

38. Final Design Principle
The AI-ConneX Data Profiler converts a compiled dataset from a structurally usable artifact into an understood, contextualized and traceable data asset. Its most important output is therefore not the statistics themselves; it is the machine-readable manifest that preserves why the data exists, how it was compiled, what was discovered about it, how confident those discoveries are, and whether the dataset is suitable for the next AI-ConneX stage.
